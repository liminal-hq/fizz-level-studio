The Fizz builder language

A Fizz script is a plain text description of one level, written and read by the studio, by a person and by Claude. A small exporter turns it into the Rust calls that a hand-written level makes, so the game does not change. This is version 0.

{{t.label}}

In one minute

level "Crater Fields" 192x28 ground=4 id=crater
start 3,4

terrain
  flat 14, up 2, flat 6, down 2

blocks
  block   x=49..51 y=10

treats
  soda    x=36 y=5

enemies
  gloop   x=35,62,85

edits   // painted in the studio
  paint one-way x=26,28,30 y=9

Each line does one thing. The first line names the level, its size in tiles, the ground height it starts at, and which level it is. start says where Ben begins.

The sections are labels for readers: terrain lays down the ground, blocks places tiles and platforms, treats places things to collect, and enemies places things that bite.

The last block, edits, is where the studio and Claude record what was painted by hand, so the lines you wrote are never rewritten.

The one rule that matters: statements run top to bottom, in file order. Later lines can overwrite earlier tiles, and items and enemies are stored in the order you wrote them. Section headers never reorder anything, and a section can appear again later.

The edits block

The edits block is where the studio and Claude record changes made on the canvas, so the script you wrote stays exactly as you wrote it.

  1. {{r}}
    2.  
edits   // painted in the studio, by you or Claude
  paint one-way x=26,28,30 y=9
  clear         x=12..14 y=8
  place cheezie x=26,28,30 y=10
Items are not tiles. Adding an enemy, a lift, a room or a switch channel is an edit. Removing a hand-written item, moving an enemy or changing the terrain is not an edit in v0: change the hand-written line, as a deliberate rewrite by a person or by Claude on request.

Overworld scripts

An overworld is a second kind of script, told apart by its header. It describes the map the player walks between levels: tiles, areas, routes and the points that launch levels. A game with several overworlds has several files.

overworld "Overworld" 60x44 id=main
start 9.2,8.2
area gumdrop-isle x=20..29 y=18..27   // the first area to match a tile decides it
blocks
  grass x=0..59 y=0..43
  river x=24..25 y=0..43
  path from=8,9 to=14,6               // a route: x first, then y
  scatter                             // trees and rocks on free grass
  house-a x=7 y=17
points
  saucer at=8,10
  level crater at=14,6
  level meteor-mesa at=16,14 req=crater
  tele crater-down at=12,19 with=meadows-up req=crater
  level citadel at=44,6 req=frosting-spire,cocoa-foundry big
  sign 0 at=8,16
  • Hand painting and the Rust way live together. Fills, routes and the scatter are the same helpers the game\'s Rust builder uses, so a script can mix painted tiles with generated ones, and the exporter writes the same calls.
  • The scatter keeps clear of every point in the file and every route drawn before it, whatever the order of the sections. Each tile rolls the game\'s own hash, so moving a point or a route changes the trees near it and nowhere else.
  • Teleporters have names. The game pairs them by their place in the point list, and the exporter works the numbers out from the file order.
  • The Episode 1 overworld, written this way, rebuilds the game\'s overworld exactly: all 2,640 tiles including its 200 trees and 32 rocks, all 27 points, the five areas and the start.
  • The game builds one overworld today, so several overworlds need a registry like the level table. Adding a level also means widening the 16-bit mask of cleared levels, which the 15 levels and the secret-found flag already fill.

How it all works in the editor

Starter levelsFile, Open starter level lists all 16 levels of Episode 1, the overworld and a small sample draft, each rebuilt from the game\'s own data. Crater Fields keeps its hand-written script; the others are written out as fills, so they are exact but not tidy.
Tiles and objects are differentTiles are painted, many cells at a time, and each paint adds a line to the end of the edits block. Objects (lifts, rooms, the boss arena, switch channels, and on an overworld the level points, teleporters, signs and the saucer) have a few properties and one line each. The studio owns that line: change an object and its line is rewritten in place, which is why moving a lift does not add a second one. Lines you did not touch are never rewritten.
The object toolsIn a level, Lift (L) drags from one end to the other, Room (R) drags a rectangle and Arena (A) drags a width. With Select, drag the A and B ends of a lift to move it, or drag a room. The Objects window lists everything, edits the selected object field by field, and sets which switch channels start on. Delete removes the selected object, and Undo brings it back.
The overworld designerOpen the overworld and paint it like a level. Pick Point (P) and a kind in the Objects window, then click the map; drag a point to move it. A level point changes which level it launches with the arrows on its Level field, and its Unlocks chips set which levels must be cleared first. The Links lens draws the unlock lines and the teleporter pairs, and the Areas lens outlines the regions.
The Paths lensShows where walking enemies go, worked out from the game\'s rules: a gloop walks until a wall or until the ground ahead ends, a marsh turns only at walls, a drone flies a fixed oval and a hopper wakes inside a box. Slopes are approximate. The real editor asks the game itself for exact paths, once the game exports them.
Code completionStart typing in the box under the script. Suggestions come from the language docs: statement words first, then tile or item words after paint and place, then field names such as from= and dwell=, then values for req= and with=. Arrow keys move, Tab accepts, Escape closes, and Enter adds the line as before. Every word in this manual is in the list.
Scripts and Rust togetherA level can be a script that exports to Rust, or hand-written procedural Rust that the editor reads by its data, as it did for all 16. Terrain runs, scatter, routes and the ladder and stairs statements keep the generated, procedural style inside a script, and painted fills sit beside them.

Using it from the command line

# parse, report errors, and check that printing gives the text back
bun packages/language/src/cli.ts check levels/crater.fizz

# write `fn crater_fizz() -> LevelData` for the game
bun packages/language/src/cli.ts export levels/crater.fizz crater_fizz out.rs

# the tests, and the proof that crater.fizz rebuilds crater()
bun test packages/language
bash scripts/prove-crater.sh
The generated function calls the Builder's private pieces, so it has to live in levels.rs or in a child module of it that starts with use super::*;. The exporter writes the function only: a new level still needs its id constant and its row in the level table by hand.
